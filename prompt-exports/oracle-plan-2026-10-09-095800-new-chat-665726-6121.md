# Deferred snapshot completion: decision and next missing fact

## 1. Summary

**Decision: STOP the deferred-completion candidate. Do not build it.**

Safety is not the blocker. The existing `VulkanCopyPool` ownership (`pending`, `source`, `Retirement`, the `strong_count` slot gate) can support completing the previous copy at the start of the next `copy_frame`. Only one consumer-acceptance fact is unverified.

The blocker is plausibility and measurability:
- **No GPU-side change.** Deferral changes no GPU submission, so frame GPU-ready time is unchanged. The 7.873 ms host wait would move from the decoder worker to the publisher's existing `DecodeSync::wait`, not disappear.
- **Small, bounded gain.** The steady-state end-to-end gain is capped by publisher pickup delay (at most the 2 ms default publish poll interval, mean about 1 ms, possibly about 0) plus at most about 0.3 ms for packets that arrive while the worker would have been blocked.
- **No valid comparison is available:**
  - Worker metrics would record relocation as a roughly 7.5 ms fake gain.
  - The T7 probe is invalid for unmarked outputs.
  - Qt cadence metrics are shift-invariant and noisier between windows than the effect.
  - Same-allocation Quit/Resume is unproven.

**The specific missing fact:** how much of the 7.873 ms is the GPU decode tail versus post-decode copy completion (copy-queue wait plus copy execution). Only a material post-decode share points to a client change that actually advances GPU-ready time.

**Single next move:**
- One descriptive window using a minimal split inside the existing probe owner. It adds one host timeline wait and one clock read, only when `OPENNOW_VULKAN_FRAME_TIMING=1`.
- One read-only check of copy-queue identity.
- No optimization, no gain claim, no matched comparison needed.

## 2. Current-state analysis

**GPU dependency chain for frame N** (`vulkan_copy.rs`, `ffmpeg.rs`)
1. `send_packet` submits decode N. T7 shows about 0.30 ms of host time from send to receive.
2. In `submit_copy`:
   - the copy waits at `ALL_COMMANDS` on the decoder timeline values from `source_waits(...)`;
   - its first barrier has source stage `ALL_COMMANDS`, so it is also ordered after all earlier work on `self.queue`.
3. The copy signals decoder value+1, written back by `update_source_signals`, and signals `slot.semaphore_value + 1`.
4. Decode N+1 is assumed to wait on that bumped value whenever N is a reference. This assumes FFmpeg's DPB/output-coincide model and must be validated. If DPB and output are separate, the bound in §3A.2 still holds, limited to the copy duration for queued frames.

**Host chain today**
1. Worker: `wait_for_fences` (T7 mean 7.873 ms).
2. Worker: `semaphore_value += 1` via `Arc::get_mut`, then `with_completed_gpu_copy()`, then enqueue.
3. Monitor (`media.rs` `run_embedded_linux_monitor`): `try_recv_latest_frame` on the next pickup. `embedded_linux_publish_poll_interval` defaults to 2 ms; the wake mechanism after L3320 is unverified.
4. Publisher: `producer.frame()` skips `DecodeSync::wait` because the frame is a completed copy.
5. `prepare()` → `wait_for_decode` with timeout 0 (revalidation only), then Qt's GPU wait.

**Implication:** frame-ready time R_N is fixed by GPU decode plus copy. A host-side handoff change can only remove the pickup and wake work that happens after R_N.

## 3. Design

### A. Candidate verdict

**A1. Safety: implementable, no blocker found**

| Hazard | Existing support | What the deferred design would need |
|---|---|---|
| Single `fence` and `command` reused | `reset_fences` / `reset_command_buffer` in `submit_copy` | Complete the previous copy first in `copy_frame`, before any validation return, slot selection, `retain` pruning, or reset |
| Published slot dropped early by a mailbox skip (`strong_count` returns to 1 while the GPU is still writing) | `strong_count == 1` gate | Completing first makes the gate sufficient again |
| Timeline monotonicity | `semaphore_value += 1` after the fence | Move the increment and `initialized = true` to immediately after a successful submit, before any fallible step |
| Source lifetime | `self.source`; `Retirement { pending, _source, _slots }` | Retain until the next completion; Drop with `pending = true` becomes routine on an existing path |
| Completion failure | `failed` + `invalidate()` | The error lands on the next frame; the previously published frame fails in `DecodeSync::wait` and surfaces as `OutputError` |
| Unmarked snapshot accepted by consumer | `frame()` waits on the timeline; `prepare()` revalidates | **Unverified:** `VulkanVideoFrame::validate`, `validate_direct_frame` and `timeline_waits` with `device_context = 0` and `lock_queue: None` |
| Probe | Qualifies outputs only if `completed_gpu_copy` | Must be mutually exclusive with frame timing |

**A2. Bounded effect.** GPU-ready time for frame N is unchanged. The gains come from two places:
- **Steady state.** The publisher already holds the frame and wakes from the timeline wait at R_N. This saves worker post-wake work (microseconds) plus pickup phase: at most 2 ms, mean about 1 ms if the monitor polls, about 0 if it is notification-driven.
- **Queued packets.** Decode N+1 is submitted earlier, but on the GPU it still waits for copy N. The saving is at most `sendReceive` (0.30 ms) plus one wake. T6 and T7 show in-flight 0–1, so this case is rare.

The expected mean is at most about 1 ms, below the pre-registered 2.0 ms materiality bar.

**A3. Measurability: the concrete blocker**
- **Worker metrics.** Session `call`/`residence` and T7 `conversion`/`fenceWait` would drop by roughly the fence wait through relocation alone.
- **T7 probe.** Unmarked outputs fall into the non-qualifying `_` arm of `drain`, so it produces no ratio.
- **Qt metrics.** `observe-stream.py` measures intervals and lateness at 1 ms resolution. Those are invariant to a constant latency shift.
- **Window-to-window noise.** On the same decode path, late frames went from 0.718% (T6) to 0.854% (T7), and video drops from 0 to 12. That variance exceeds any 1 ms effect.
- **What attribution would need.** A per-frame span from a fixed origin (submission → publish or import) crossing `session.rs` → `media.rs` → `frame_producer.rs`. That is the multi-file trace that was excluded.

```rust

pub(crate) enum DecodeReadySplit { Measured(Duration), TimedOut, Failed }
pub(crate) struct FenceWait { pub total: Duration, pub decode_ready: DecodeReadySplit }

impl FenceWaitObservation {

        &mut self,
        decode_ready: impl FnOnce() -> ReadyWait,
        fence: impl FnOnce() -> Result<(), E>,
    ) -> Result<(), E>;
}
```

`measure_split` replaces `measure`, which has a single call site, so there is no parallel path.

| Mode | Behavior |
|---|---|
| Disabled | Calls `fence()` once. No clocks, the `decode_ready` closure is never invoked, nothing is stored. Identical to today. |
| Enabled | t0 → `decode_ready()` → t1 → `fence()` → t2. Stores `total = t2 − t0` (same position and meaning as T7 `fenceWait`). Sets `Measured(t1 − t0)` only on `Reached`. Returns the fence result unchanged. On fence error, behaves exactly like T7's error path. |

## 3. Design

### Constructor gate and measurement separation

In `FfmpegDecoder`, cache `OPENNOW_VULKAN_DEFER_SNAPSHOT_WAIT` once, scoped to `FfmpegMode::Vulkan` with `shared_device`. Only `"1"` enables deferral; all other values retain synchronous behavior. Pass the boolean into the lazy pool constructor.

### Pool state and lifetimes

- After the failed-device guard, complete any previous pending submission before validation, slot pruning/selection, command reset, or source release.
