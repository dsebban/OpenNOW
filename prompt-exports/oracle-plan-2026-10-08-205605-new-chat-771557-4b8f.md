### 3.1 Live receive-thread counters (support instrumentation, no behavior change)

**New type `ReceiveServiceCounters`.**
- Kind: private struct in `nvst.rs`.
- Owner: a local value inside the UDP video receive loop function. It is single-threaded, never shared, and takes no locks.

```text
ReceiveServiceCounters {
  svc_max: Duration, svc_gt_1ms: u32, svc_gt_5ms: u32,          // recv-return → end of datagram handling
  gap_max: Duration, gap_gt_5ms: u32, gap_gt_10ms: u32, gap_gt_20ms: u32, // data recv-return → next recv_from call
  last_data_returned: Option<Instant>,
  sched_prev: Option<SchedStat>,                                 // (cpu_ns, runq_wait_ns, slices)
}
fn parse_schedstat(text: &str) -> Option<SchedStat>             // pure, compiled on all targets
before_recv(at: Instant)               // if last_data_returned is Some → update gap stats, clear it
data_returned(at: Instant)             // sets last_data_returned
data_serviced(returned_at, done_at)    // svc stats
interval_fields(&mut self) -> String   // " rx_svc_max_us=… rx_svc_gt1ms=… rx_svc_gt5ms=… rx_gap_max_us=…
                                       //   rx_gap_gt5ms=… rx_gap_gt10ms=… rx_gap_gt20ms=…[ rx_cpu_ms=… rx_runq_ms=… rx_slices=…]"
                                       // resets maxima/counts; schedstat deltas only when a prior snapshot exists
```

**Loop wiring.** Add exactly three timestamps:
- Call `Instant::now()` immediately before `socket.recv_from`, then `before_recv`.
- At the top of the `Ok((length, source))` arm, store `data_at = Some(Instant::now())`, then `data_returned`.
- After the `match`, if `data_at` is Some, call `data_serviced(t, Instant::now())`. The arm is a labeled block with `break 'datagram`, so this measurement must sit after the match, not inside it.

Leave everything else alone. Do not touch the existing `received_at`, STUN, process, or forward logic.

**Schedstat read.** Inside the existing 10 s stats branch, on `#[cfg(target_os = "linux")]` only, read `/proc/thread-self/schedstat`. The stats branch runs on the receive thread, so `thread-self` is correct. Parse it with `parse_schedstat`. On any read or parse failure, omit those three fields silently.

**Emission.** Append `interval_fields()` to the end of the existing `nvst-video` `log_async` format string only.
- Do not change the `eprintln!` rx-stats line, the `media-timeout` line, or any timeout, recovery, keepalive, or drop code.
- The collector only parses `type=telemetry` rows, so the extra fields do not affect it.

**Cost.** About 3 `Instant::now()` calls per datagram, roughly 60–100 ns with vDSO/TSC, which is under 0.1 % of the ~95 µs average per-datagram budget. Add one small `/proc` read every 10 s. The replay reports measured `Instant::now()` cost to confirm.

**Why always-on, not env-gated:** it avoids adding a runtime flag dimension to attribution, and the cost is below measurement noise.

### 3.2 Local replay: `nvst/receive_replay.rs` (test-only)

Declare it in `nvst.rs` as `#[cfg(test)] mod receive_replay;`. The file lives at `src/nvst/receive_replay.rs`. As a child module it can reach private items, and nothing ships in release builds.

**Fixed profiles.** Each runs 20 s simulated at 60 fps and 100 Mbps, with the payload size taken from the code's packet-size constant (fallback 1408 B). Keyframes occur at t=0 and every 10 s at 6× average size, which is ≈ 1.25 MB, about 888 datagrams.

| Profile | Loss / reorder | Arrival model |
|---|---|---|
| P0 `steady-wifi` | none | Wi-Fi A-MPDU: bursts of 32 datagrams at 1 µs spacing; burst cadence set by 400 Mbps effective |
| P1 `loss-fec-wifi` | 1 % random loss, FEC-recoverable; 0.5 % adjacent swaps | same as P0 |
| P2 `burst168-wifi` | one 168-datagram consecutive loss at t=10 s, then a keyframe 6 frames later | same as P0 |
| P3 `steady-wired` | none | line rate 1 Gbps |

FEC uses the code's default percentage if a constant exists; otherwise 20 % (assumption, recorded in the report).

**Generator.**
- Streams per frame, so the full trace is never held in memory.
- Uses a seeded xorshift64*, so no new dependency.
- Reuses the existing nvst.rs test fixtures for protected NV video packets.
- FEC shards come from the encode counterpart of whatever Reed-Solomon implementation the receiver decodes with.
- If no encoder exists, mark the report `fec_reconstruction: not_exercised`. This caps the verdict at INCONCLUSIVE for the FEC class.
- Generator metadata tags each frame as `clean`, `lossy`, or `post_burst_keyframe`.

**Service runner.**
- Fresh receiver with test keys. Simulated time is `base + arrival_ns`, and that simulated time is passed as `now`, so reorder, NACK, and timeout logic follow the arrival model rather than bench speed.
- For each datagram, time one block: `process_datagram` → each event through `forward_receive_event` → `poll_receiver_report(now)` → `poll_timeout(now)` → `poll_frame_progress` (if the loop calls it). Housekeeping must match the loop's order exactly, with a comment pointing at the loop.
- Drain the media consumer **outside** the timed region. That is the consumer thread's work in production, and draining also prevents artificial backpressure.

**Service classes:** `Packet`, `FrameComplete`, `FrameCompleteAfterLoss` (which implies reconstruction or reorder flush), `Discontinuity`. Classes come from the returned events plus generator metadata, so there is no dependency on stat names.

**Queue simulation (O(n) time and memory).**
1. Compute scaled service `ŝ_i = k·s_i + r`, where `k ∈ {1, 3}` and `r = max(measured local loopback recv cost, 3 µs)`.
2. Compute recv start `start_i = max(a_i, d_{i−1})` and departure `d_i = start_i + ŝ_i`.
3. Kernel occupancy at arrival is `occ_i = i − #{j<i : start_j ≤ a_i}`. Because `start` is nondecreasing, a single pointer suffices.
4. Report max occupancy with its time and class, and set `would_overflow = max_occ ≥ B`.

Drops are not modeled, because the verdict only needs the threshold crossing. `k = 3` is the conservative NucBox and contention factor, since the dev host CPU differs from the target.

**Bench test (`#[ignore]`).**
- Panics if `cfg!(debug_assertions)`, i.e. if not run in release.
- Runs P0–P3 × 3 repetitions.
- Prints one line, `RECEIVE_REPLAY_JSON {…}`, containing:
  - Host: arch, CPU string, `instant_now_ns`, `r`, B inputs.
  - Per profile and repetition: datagrams, frames assembled versus expected, `fec_exercised`, service p50/p99/p99.9/max, throughput, the top 5 slow samples with class, `max_occ` at k=1 and k=3, and the verdict.

**Deterministic tests (default `cargo test`, run on every build):**
- `replay_trace_is_deterministic`: two generations hash-equal.
- `replay_assembles_expected_frames`: in P0 and P1, assembled frames equal generated frames, and no timeout or recovery fires. This guards against false reassurance from, for example, auth failures that make service times tiny.
- `replay_burst_loss_surfaces_discontinuity`: P2 produces the expected drop/gap event and assembles the post-burst keyframe.
- `queue_sim_matches_hand_computed`: hand-checked cases for the recurrence.

#### Owned data

Keep the harness small, with two test-local records:

| Record | Fields and ownership |
|---|---|
| `ReplayPacket` | Immutable `arrival_offset_ns: u64`, `source: SocketAddr`, and owned `datagram: Vec<u8>`. Built before timing and reused across repetitions. |

The conceptual interfaces are:

- **`replay_serial_packets`**: packet slice + fresh receiver + fixture consumer → ordered timing samples and frame/event trace.

Both are synchronous, local and bounded. Fixture construction or semantic mismatches fail the corresponding test. A performance result must not be emitted as valid after such a failure.

#### Actual processing path

For each packet:

1. Supply the fixture’s source, bytes and scripted monotonic instant to the existing `process_datagram`.
2. Forward every returned event through the existing `forward_receive_event`.
3. Measure processing, forwarding and the combined service interval.
4. After the measured interval, collect counter deltas and drain test-owned event/output channels.
5. Store the numeric sample.

### 3.4 Backlog calculation and its limits

For the recorded no-loss service trace, calculate serial completion times:

\[
start_i=\max(arrival_i,finish_{i-1}),\qquad
finish_i=start_i+service_i
\]

Process a completion before an arrival when timestamps are equal. Count queued packets and their datagram bytes separately from the packet currently being serviced.

Report:

- Maximum waiting packet count and datagram bytes.
- Maximum queue wait.
- Completion relative to the next 60 Hz frame boundary.
- Whether backlog grows across consecutive frame periods.

This is a **service-demand model**. Datagram bytes are not kernel socket memory, and the model does not predict an exact number of socket drops. It also does not rerun protocol decisions after modeled delays or losses.

Validate its arithmetic with small deterministic cases: adequate paced service, a burst that drains, sustained overload, and one injected long service interval. The injected interval validates the estimator only; it is not evidence of a production stall.

The model and reporting are linear in packet count; retained fixture and trace storage are also linear.
