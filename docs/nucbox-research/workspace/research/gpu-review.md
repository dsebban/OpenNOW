# Linux GPU decode and presentation review

Reviewed the current Qt/Rust desktop source at `bee18c118dbc89f42319436dcdb172d5b9e15e0c`. Source references below are relative to `vendor/OpenNOW`; line numbers refer to this pinned revision. This was a source review, with no build, GUI operation, vendor edit, credential access, or capture analysis.

The most useful starting point is OpenNOW's existing VA-API P010 decode and Vulkan import path. Reuse its native frame ownership, conversion shader, QRhi integration, and recovery contracts. Prove the full path on this AMD machine before changing presentation scheduling. Vulkan Video is a candidate comparison after that proof, not an established replacement.

The supplied host evidence is Ryzen 7 5700U Lucienne/Renoir, Mesa 25.1.1, VA-API H.264 and HEVC Main10 VLD support, and no AV1 decode profile. An installed Vulkan 1.4 library does not establish decode extensions, per-profile support, DMA-BUF modifier compatibility, or performance. The official client's bounded observation was H.265 10-bit 1080p60 on an X11 1720×1440 60 Hz desktop, with 58–59 ms ping, 59–60 game FPS, 60–61 stream FPS, and zero reported loss. Those FPS/loss readings do not measure scanout spacing or custom-client behavior.

## Existing implementation worth reusing

| Component | Implemented behavior and source |
| --- | --- |
| Negotiated decode selection | Embedded automatic selection first checks a shared Vulkan device against codec, pixel format, and dimensions. Fallback supports VA-API 10-bit 4:2:0; CUDA/V4L2 are excluded for this depth. `native/opennow-streamer/crates/opennow-streamer-platform/src/linux_backend.rs:136–229`, `media.rs:1274–1289`. |
| VA-API profile selection | Probes VLD entrypoints and render-target depth, including HEVC Main10. FFmpeg picks a device supporting the required depth. Hardware codec thread count is one. `platform-linux/src/video/vaapi_probe.rs:57–79,159–175`, `video/ffmpeg.rs:150–205`. Here and below `platform-linux` abbreviates `native/opennow-streamer/crates/opennow-streamer-platform-linux`. |
| GPU frame export | FFmpeg maps hardware output directly to `DRM_PRIME` with `AV_HWFRAME_MAP_READ | DIRECT`, preserves frame PTS, and verifies VA-API output depth against negotiation. `platform-linux/src/video/ffmpeg.rs:484–521,988–1019`. |
| P010 DMA-BUF import | Imports NV12/P010 with the actual modifier, pitches, offsets, foreign queue ownership, and duplicated FD. Accepts composed or split-plane layers sharing one object; disjoint multi-object layouts fail explicitly. `platform-linux/src/frame_producer.rs:2022–2065,2086–2267`. |
| Conversion and Qt composition | Native code records YUV conversion into Qt's Vulkan command buffer, producing a per-slot RGB texture. P010 SDR can use RGB10A2; metadata drives matrix, range, transfer, and chroma placement. Qt imports the opaque resource with `QRhiTexture::createFrom`, then draws it in the same scene graph as overlays. `platform-linux/src/frame_producer.rs:624–682,1316–1355`; `opennow-qt/src/streaming/rendering/NativeStreamRenderCallback.cpp:169–278`; `StreamVideoTextureRenderer.h:92–106`. |
| Surface lifetime | Native slot ownership retains the decoded source. Import cache keys include FD device/inode, depth, dimensions, modifier, and plane layout, with weak references. Qt maintains imports per QRhi slot. `platform-linux/src/frame_producer.rs:668–682,814–849`; `StreamVideoTextureRenderer.h:14–16`. |

This is GPU decode followed by a GPU conversion pass and Qt composition, with no normal CPU readback for P010. It is not direct YUV scanout. The distinction matters when estimating memory traffic and display latency. Ten-bit decoding also does not imply HDR: transfer and primaries are separate fields in `platform-linux/src/format.rs:45–69`. Qt logs texture and output bit depth, and an 8-bit output uses dithering in this renderer, `NativeStreamRenderCallback.cpp:265–276`.

The import code already handles 1080-to-1088 coded-height padding and samples only visible rows. Preserve this logic; a simplified importer can introduce displaced chroma/tint at the target resolution. `platform-linux/src/frame_producer.rs:2103–2118,1317–1324`.

Qt requests external-memory, DMA-BUF, DRM-modifier, and foreign-queue extensions. Its import contract checks the requested and advertised extensions, `opennow-qt/src/streaming/rendering/LinuxVulkanGraphics.h:51–91`. Those checks do not prove that this driver's exported P010 modifier is importable and sampleable. The shader/import/lifetime path needs a real AMD run.

For Vulkan Video, OpenNOW creates a shared device, reserves a Qt graphics queue, removes it from native decoder/copy ownership, and validates negotiated formats. Qt adopts that device before exposing its window and checks presentation support. `platform-linux/src/vulkan_device.rs:472–584,588–637`; `LinuxVulkanGraphics.cpp:90–109`. Decoder readiness waits run on the publisher thread; render preparation rechecks with a zero-timeout semaphore wait and records a GPU queue wait. The readiness timeout is one second, not a frame budget. `platform-linux/src/frame_producer.rs:23,249–275,770–811`. Device teardown also waits for the render queue, `frame_producer.rs:130–152`; this should not be mistaken for a normal per-frame wait.

## Queue and pacing findings

At 60 FPS there are two compressed queues: ingress holds `ceil(fps/4)`, therefore 15 frames, and the Linux decoder command queue defaults to 16. Decoded output holds three frames. Defaults permit 1–64 compressed and 1–16 decoded frames. `platform/src/media.rs:114–119,1292–1295`; `platform-linux/src/session.rs:98–119,210–211`. The compressed capacity alone represents roughly 0.52 seconds at 60 FPS if both queues fill. This is a capacity calculation, not measured steady-state latency. Decoder internal surfaces and Qt/compositor buffering are additional stages.

Compressed overflow invalidates the prediction chain, rejects delta frames until a valid keyframe, preserves control commands, and requests recovery. Do not replace this policy with arbitrary compressed-frame dropping. `platform-linux/src/session.rs:471–536`; `platform/src/media.rs:3092–3113`. Decoded frames can safely discard older outputs and count skips, `session.rs:1325–1338`; `media.rs:3212,3252–3257`.

The embedded monitor selects the newest decoded frame, publishes it into a one-frame mailbox, and sleeps two milliseconds between passes. Publishing replaces an unread previous frame; the monitor ignores the returned replacement outcome. Decoder skips are counted, but mailbox replacement is not counted here. `platform/src/media.rs:3191–3277,3371`; `platform/src/graphics.rs:391–415`.

For ordinary embedded Qt video, a frame-available callback requests an item update; Qt's render thread consumes the latest mailbox entry and the window's swap cadence controls presentation. `StreamVideoItem.cpp:78–79,383–389`; `NativeStreamRenderCallback.cpp:218,400–405`. The Rust `LinuxFramePacer` with adaptive 0–2-frame buffering belongs to the standalone SDL/Vulkan output owner, `platform/src/output.rs:462,509`. It is not called by the embedded Qt monitor. Qt's `StreamFramePacer` is gated behind frame generation, `NativeStreamRenderCallback.cpp:284–287`, and requires approximately twice the source refresh, `StreamFramePacer.h:75–77`. At 60 FPS on 60 Hz, interpolation is unsuitable.

Two instrumentation limits deserve attention. Linux frame handles receive a local sequential counter, `platform-linux/src/frame_producer.rs:275`, so interpolation's sequence-gap detection cannot establish sender frame loss. Presentation timestamps retain decoded media PTS, `frame_producer.rs:297–298`. Also Qt's submit/swap statistics are callback measurements, not physical scanout or input-to-photon timestamps, `NativeStreamRenderCallback.cpp:400–405,454–463`.

## Three bounded experiments

1. **Prove HEVC Main10 VA-API to Qt.** Use a non-secret local 1080p60 test clip with motion and color bars in the fork. Record selected codec/profile, exported P010 layout/modifier, successful Vulkan import, conversion/output bit depth, decode residence, CPU use, and GPU load. Check padded chroma, limited/full range, and ten-bit gradients. Exercise resize, fullscreen, overlays, and graphics-resource recreation. Pass requires no CPU download and stable ownership, not merely a successful VA-API query. Keep AV1 disabled on this host.

2. **Measure queue age and display pacing.** Instrument ingress/decoder depth, frame age at dequeue/publish/record, decoded skips, mailbox replacements, and Qt submit/swap deltas. Compare fixed-duration repeated 1080p60 motion runs with the official-client observation conditions. Report medians and p95/p99 frame intervals and age. Change one variable per run: replace the two-millisecond publisher poll with a wakeup, then compare one smaller compressed queue capacity while preserving keyframe recovery. Keep frame generation off. Retain a change only when age or missed presentation deadlines improve without reset/corruption increases.

3. **Compare shared Vulkan Video only after capability proof.** Enumerate actual codec/depth/dimension and queue-isolation support, then use the same clip and measurement procedure against proven VA-API. Reject unsupported P010 or unavailable isolation. Measure decode residence, GPU copy/conversion work, queue waits, and output pacing; do not select Vulkan on API version alone. The implemented FFmpeg GPU snapshot path merits reuse if measurements justify it, `video/ffmpeg.rs:380–419`.

None of the supplied observations shows a loss workload that warrants GPU FEC work. Decode/import compatibility and presentation timing have concrete implemented components and measurable gaps; prioritize those experiments.
