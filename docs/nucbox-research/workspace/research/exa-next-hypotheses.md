# Next Linux presentation hypotheses

Exa CLI research used targeted primary-source searches, archived Qt 6.9 documentation and exact Qt 6.9.1 source. Local OpenNOW source was read at `3c85a3d`. No GUI, account, environment, power, display or network setting changed; no build or test ran. None of the earlier polling, continuous-update, basic-loop, idle-zero, VA-API or receive-buffer candidates passed acceptance. The proposals below have no measured benefit yet.

The machine is AMD Lucienne/RADV RENOIR under GNOME X11. Saved XRandR evidence exposes 3440×1440 at 60, 85, 100 and 120 Hz, with 60 Hz current and identity transform. `vrr_capable` was zero in that readback. That does not justify assuming an active VRR path. Graphics clocks previously reached 1900 MHz under the packaged manual/3D_FULL_SCREEN policy, so one low-clock reading is not proof of a fixed clock cap.

## 1. Display grid at 120 Hz

Qt emits `frameSwapped` when a frame is queued for presentation and limits it to at most one per vsync interval in a continuously animating scene. Halving that interval gives a ready source another opportunity before the next 60 FPS source deadline. This is an inference from the presentation grid, not a guarantee that Qt or the GNOME compositor will use every opportunity. The callback is not physical scanout. [Qt 6.9 QQuickWindow](https://doc.qt.io/archives/qt-6.9/qquickwindow.html).

Use a new matched block: 60 Hz baseline, 120 Hz candidate, 60 Hz closing control, with identical build, scene, cloud session, codec, resolution, 60 FPS offer, queues, fullscreen and overlays. Keep frame generation off and the primary fresh-source late threshold at 25 ms. The existing refresh validator expects 60 Hz, so the new block must explicitly permit its intended display rate before scoring, without reclassifying old verdicts. Count fresh-source FPS separately from all-window FPS. Higher refresh can double composition work and increase power or queue contention. Require unchanged latency/FPS/error gates and verify restoration of 60 Hz. A 100 Hz display has a non-integer relationship to the 60 FPS source; it is not a preferred next variation without evidence that 120 Hz introduces a specific problem.

## 2. Depth/stencil attachment experiment

This switch exists in the actual version. `QSGRenderThread::ensureRhi` in Qt 6.9.1 creates a swapchain depth/stencil renderbuffer only when `QSG_NO_DEPTH_BUFFER` is empty. It does not disable vsync or select a different decoder. [Exact Qt 6.9.1 threaded-loop source](https://raw.githubusercontent.com/qt/qtdeclarative/v6.9.1/src/quick/scenegraph/qsgthreadedrenderloop.cpp).

The applicability constraint is in OpenNOW. `opennow-qt/src/streaming/rendering/StreamVideoTextureRenderer.h:271` enables depth testing, `:278` enables stencil for clipped rendering, and `StreamVideoItemRendering.cpp:74` declares `DepthAwareRendering`. Removing an attachment is therefore not presumed safe. Validate ordinary video, overlay text/menus, clips, layering, resize/fullscreen and surface recreation before timed playback. Keep render loop, stream and display unchanged. Reject any broken visual/input behavior or higher frame-age/CPU tails. If the no-attachment path is incompatible, stop; do not silently change native pipeline flags in the same attempt.

If this conditional preflight fails, prioritize the independently scoped event-driven frame publisher over a broad synchronization rewrite. Wake the existing bounded latest-frame owner when decode output becomes available, preserve latest selection and readiness waits, and make stop/recovery wake that owner. This targets polling-phase delay without intentional buffering. It needs its own evidence and shutdown verification; the earlier 1 ms polling result is not proof that an event-driven publisher will help.

## 3. Vulkan dependency scope

Local `frame_producer.rs:788` submits a decoder timeline wait at `ALL_COMMANDS`; `:1274` uses an acquire barrier beginning at `ALL_COMMANDS` before fragment conversion. `video/vulkan_copy.rs:651`, `:693` and `:721` also use broad scopes around copy/restore and semaphore waits. These paths are under `native/opennow-streamer/crates/opennow-streamer-platform-linux/src/`. Broad synchronization can reduce overlap, but it is not evidence that this workload is currently synchronization-bound. Khronos's sample demonstrates the conservative-versus-specific-stage mechanism; its performance result is not a Lucienne benchmark. [Khronos pipeline-barrier sample](https://docs.vulkan.org/samples/latest/samples/performance/pipeline_barriers/README.html).

First separate CPU snapshot-fence wait, native preparation, Qt recording and GPU execution time. Qt 6.9 supports GPU timestamps through `QSG_RHI_PROFILE=1` or `QQuickGraphicsConfiguration::setTimestamps`, with timing output through render-loop logging. This is diagnostic work with overhead, not a candidate win. [Qt 6.9 graphics configuration](https://doc.qt.io/archives/qt-6.9/qquickgraphicsconfiguration.html).

If a dependency is proven over-broad, test a single narrower stage/access scope on the completed H.264 GPU-snapshot path. Keep the copy and its source retention. Never delete the blocking fence merely because it costs time: `vulkan_copy.rs:381` protects source reuse. An asynchronous copy/timeline design needs multiple bounded pending slots and retirement; it is a redesign, not a one-line optimization. Validate memory/layout/ownership correctness and corruption/device-loss/recovery behavior before live scoring. Fewer waits or drops cannot justify stale/corrupt frames.

## Useful ideas that are not cheap knobs

`QRhiSwapChain::MinimalBufferCount` is present in archived Qt 6.9. Exact `qrhivulkan.cpp` requests `max(2, surface minimum)` when it is set, rather than the usual request of up to three images. It **does not change QRhi frames in flight**. Qt 6.9.1's threaded-loop creation does not expose this flag through a verified environment variable; applying it requires respecting Qt's swapchain/render-thread lifecycle and observing actual image count. Treat it as a later integration candidate, not an invented switch. [Qt 6.9 swapchain](https://doc.qt.io/archives/qt-6.9/qrhiswapchain.html), [Exact Vulkan backend](https://raw.githubusercontent.com/qt/qtbase/v6.9.1/src/gui/rhi/qrhivulkan.cpp), [GraphicsStateInfo](https://doc.qt.io/archives/qt-6.9/qquickwindow-graphicsstateinfo.html).

Moonlight's current pacer separates pacing/render queues, bounds queued frames and uses a 3 ms scheduling slack. Its selected vsync-source implementations cover Windows and Wayland; other platforms fall back to immediate rendering. This is architecture evidence, not an X11 fix to copy blindly. PR 1139 proposes minimum buffered latency but remains open; its user tests are not an accepted upstream improvement and intentional buffering must satisfy this user's latency guard. [Moonlight pacer source](https://raw.githubusercontent.com/moonlight-stream/moonlight-qt/master/app/streaming/video/ffmpeg-renderers/pacer/pacer.cpp), [Open buffering proposal](https://github.com/moonlight-stream/moonlight-qt/pull/1139).

Qt 6.9's `QThread::setServiceLevel` has no Linux implementation, and priority effects depend on OS scheduling policy. There is no verified `QSG_RENDER_THREAD_PRIORITY` environment path in the examined 6.9.1 loop. Do not advertise either as a Linux low-latency fix. [Qt 6.9 QThread](https://doc.qt.io/archives/qt-6.9/qthread.html).

Use the additive all-window/fresh-source and oldest/latest GUI-drain census to choose between phase delay and upstream starvation. Preserve local socket-loss and network context. None of these callbacks alone establishes physical scanout timing or input-to-photon latency.
